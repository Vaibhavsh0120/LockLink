# LockLink v1.9.2

Source version **1.9.2+192**. App, firmware diagnostics, and all three iOS widget
build configurations identify this version. Android and iOS app versions derive
from the Flutter build configuration. This document records the local source
audit on 30 September 2026; it does not establish a published release.

## Changes included

- Wider tablet and desktop door cards; the Settings widget card sits beneath
  Device in the two-column layout. The compact phone layout is preserved.
- The Matter accessory is a door lock: Unlock starts the existing two-second
  release, Lock stops it early. Its state describes the output, not door position.
- Connected homes can be added, renamed, and individually removed. Removing a
  stale home allows commissioning again without clearing Wi-Fi, other homes,
  or the app key. Pairing credentials remain private and temporary.
- Home records and names live on the door. Foreground app clients refresh them
  about once per second; a missed mutation reply is never replayed.
- Terminal Send can wait for a current read-only poll; it preserves a newer
  draft and cancels a pending send across lifecycle changes or disconnects.

## Audit repairs

- Settings/secure-storage failures no longer leave startup loading forever.
  Unlock stays disabled and Open Settings provides recovery. Returning from
  Settings reloads saved credentials even after a partially failed save.
- Flutter now rejects redirects, matching the native widget clients. All clients
  reject ambiguous IPv4 spellings and invalid ports. Unsafe stored addresses
  are rejected before an app HTTP request.
- Native widgets reject missing/unknown output states, invalid modes, and
  malformed boolean fields. Relay status must explicitly indicate it is armed.
  Invalid unlock replies cannot be reported as successful; ambiguous HTTP
  unlock errors in Flutter report no confirmation.
- Busy challenge responses no longer mark an otherwise armed relay unarmed.
- Terminal log contention is checked before a pairing command runs, preventing
  a busy reply after an applied mutation. Command-generated logs arrive on
  the next poll; private command output is returned immediately.
- Removed the unused `LocalApi::printStatus` method and stale Android template
  TODOs. Restored the Cupertino icon font required by platform navigation.
- Fixed the previous Linux firmware CI failure: the Matter UTF-8 header is
  `lib/support/utf8.h`. The old uppercase `UTF8.h` spelling only worked on a
  case-insensitive filesystem such as this Windows checkout.
- Release preflight validates tag/version, source commit, existing remote tag,
  Settings footer, firmware version, and iOS widget version/build consistency.
  Same-tag releases serialize, recheck before publication, and correctly mark
  prereleases. Firmware CI checks all four image files individually.
- Automatic Mobile checks cover app pushes/PRs. The manual release macOS job
  now runs native iOS tests and retains simulator/build/test diagnostics.
- Updated both READMEs and all current guides to the actual door-lock behavior,
  ecosystem restrictions, pairing management, and recovery paths. Historical
  release notes remain unchanged; the terminal plan is now a current contract.

## Platform and hardware boundaries

Connected-home entries are Matter homes/platforms, not an Apple account or
phone list. Devices and people sharing one Apple Home normally share its one
entry; separately commissioned homes/platforms have separate entries. Apple
Home manages member permissions. LockLink receives neither Apple IDs nor an
account roster. See [Matter setup](../MATTER_SETUP.md#pairing-information-reset-and-recovery).

Every LockLink client needs the saved device address and matching app key.
There is no cloud synchronization or independent app-user revocation; clients
with that key can manage the door's connected homes. Theme and haptics remain
per device. Changing an app label does not rename the accessory inside a home
platform.

Physical commissioning/removal/re-pairing, two-phone network behavior, router
loss/rejoin, relay cutoff under load, controller permissions/voice behavior,
and signed iPhone widget operation remain hardware/platform validation gates.
No door-position sensor is present. The default remains a local LED prototype;
real relay mode is explicitly configured and is not a public remote-access service.
